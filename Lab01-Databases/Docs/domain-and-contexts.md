# Предметна область та межі контекстів — «Система управління бібліотекою»

> Лабораторна робота № 01. Крок 1 і Крок 2 методики.

## 1. Опис домену

Система обслуговує **міську публічну бібліотеку**. Бібліотекарі ведуть каталог книг
(автори, жанри, фізичні примірники на полицях), оформлюють читачам видачу книг на
визначений термін, приймають повернення та нараховують пеню за прострочення.
Читачі додатково пишуть відгуки на книги, обговорюють їх і складають власні
підбірки для читання.

Три групи даних живуть за різними правилами: **каталог** змінюється рідко й має
строгі зв'язки, **видача** — транзакційний процес зі станами й грошима, **відгуки** —
слабко структурований контент із вкладеними обговореннями. Саме тому систему
розділено на три незалежні контексти, кожен зі власною базою даних.

## 2. Три обмежені контексти (Bounded Contexts)

| Проєкт | Контекст | Технологія персистентності | Чому саме ця технологія |
|---|---|---|---|
| **№1** | **Видача** (Lending) | SQL Server + **ADO.NET & Dapper** | Видача — транзакційний процес (оформлення → підтвердження → видача на руки → повернення). Потрібні збережувані процедури, явні транзакції, перевірка допустимості переходів статусів і контроль цілісності «на рівні бази». |
| **№2** | **Каталог** (Catalog) | SQL Server + **EF Core (Code First)** | Каталог — багато сутностей і всі три типи зв'язків (1:1, 1:N, M:N із власним полем). Зручно показати Fluent API, міграції та seed-дані. |
| **№3** | **Відгуки** (Reviews) | **MongoDB** | Відгуки, коментарі й обговорення мають динамічну структуру: різні читачі залишають різні набори полів (фото, теги, детальні оцінки, аудіо-відгук). Природно лягає на документи з піддокументами. |

### Розподіл сутностей (кожна належить рівно одному контексту)

**Проєкт №1 — `LibraryLendingDb`** (власник даних про видачу):
- `Readers` — читачі бібліотеки *(власна сутність контексту)*
- `Loans` — видача, коренева сутність агрегату
- `LoanDetails` — деталі видачі (1:1)
- `LoanItems` — позиції видачі (M:N між `Loans` і `Books`)
- `LoanStatusHistory` — журнал переходів статусів
- `FinePayments` — оплати пені
- `Books` — **локальна копія довідника** з Каталогу (не власна сутність!)

**Проєкт №2 — `LibraryCatalogDb`** (власник даних про книги):
- `Authors` — автори
- `Books` — книги, **власник ідентифікатора книги в усій системі**
- `BookDetails` — опис книги (1:1)
- `BookCopies` — фізичні примірники (1:N)
- `Genres` — жанри
- `BookGenres` — проміжна сутність M:N із власним полем `AddedAt`

**Проєкт №3 — `LibraryReviewsDb`** (власник контенту читачів):
- `reviews` — відгуки
- `discussions` — обговорення
- `readingLists` — підбірки книг
- `readerProfiles` — профілі читачів у контексті відгуків

### Правило належності

`Book` існує в усіх трьох контекстах, але **власник один — Каталог (Проєкт №2)**.
Контекст Видачі зберігає локальну копію довідника (`dbo.Books`) і знімки полів у
позиціях, контекст Відгуків — лише `bookId` і денормалізовану назву.
Аналогічно `Reader` належить контексту Видачі, а `readerProfiles` у MongoDB — це
окрема сутність контексту Відгуків, що лише посилається на `Readers.Id`.

## 3. Агрегати й межі даних (Крок 2)

| Контекст | Агрегат | Склад | Життєвий цикл |
|---|---|---|---|
| Видача | **Loan** | `Loans` + `LoanDetails` + `LoanItems` + `LoanStatusHistory` | Позиції не існують без видачі й змінюються лише через неї. Видалення видачі каскадно видаляє позиції, деталі та історію. |
| Видача | **Reader** | `Readers` + `FinePayments` (через `Loans`) | Читача **не** видаляємо каскадно: історія видач має зберігатися (soft delete `IsDeleted`). |
| Каталог | **Book** | `Books` + `BookDetails` + `BookCopies` + `BookGenres` | Опис і примірники не існують без книги (каскад). Жанр — довідник, живе окремо. |
| Каталог | **Author** | `Authors` | Автора не можна видалити, поки є його книги (без каскаду). |
| Відгуки | **Review** | документ `reviews` + вбудовані `comments[]` | Коментарі живуть разом із відгуком. Довга ветка винесена в `discussions` за посиланням. |
| Відгуки | **Discussion** | документ `discussions` + `messages[]` | Необмежено зростає, тому окремий документ, а не вбудовування у відгук. |

## 4. Міжконтекстні посилання — без FOREIGN KEY

```
LibraryCatalogDb.Books.Id  (ВЛАСНИК ідентифікатора книги)
        │
        ├─ ─ ─ ►  LibraryLendingDb.Books.Id        (локальна копія довідника)
        │             └─ ─ ─ ► LibraryLendingDb.LoanItems.BookId (+ знімки полів)
        │
        └─ ─ ─ ►  LibraryReviewsDb.reviews.bookId  (+ денормалізована bookTitle)
                   LibraryReviewsDb.discussions.bookId
                   LibraryReviewsDb.readingLists.items[].bookId

LibraryLendingDb.Readers.Id  (ВЛАСНИК ідентифікатора читача)
        └─ ─ ─ ►  LibraryReviewsDb.reviews.author.readerId
                   LibraryReviewsDb.readerProfiles.readerId
```

`─ ─ ─ ►` — **логічне** посилання за ідентифікатором: звичайний стовпець без
обмеження. Цілісність за потреби перевіряє прикладний код.
`─────►` (суцільна лінія) — справжній `FOREIGN KEY`, існує **лише в межах однієї
бази**.

Перевірка: `SELECT * FROM sys.foreign_keys` у кожній SQL-базі не показує посилань
за межі цієї бази (див. `verify.sql`, блок 1).

## 5. Таблиця політики дублювання даних

> Крок 2 методики. Мінімум один рядок на кожну пару контекстів, що взаємодіють.

| № | Поле | Де зберігається | Джерело (власник даних) | Політика узгодженості |
|---|---|---|---|---|
| 1 | `LoanItems.BookTitle`, `LoanItems.BookAuthor`, `LoanItems.DailyFee` | `LibraryLendingDb` (Проєкт №1) | `Books` у `LibraryCatalogDb` (Проєкт №2) | **Знімок на момент оформлення видачі — свідомо НЕ оновлюється.** Тариф і назва, за якими оформлено видачу, мають залишитися незмінними, навіть якщо каталог їх змінить. Так само `OrderItem` в eShop зберігає `ProductName` і `UnitPrice`. |
| 2 | `Books.Title`, `Books.Author`, `Books.Isbn`, `Books.DailyFee` (локальна копія довідника) | `LibraryLendingDb` (Проєкт №1) | `Books` у `LibraryCatalogDb` (Проєкт №2) | **Копія для читання — оновлюється подіями з Каталогу** (`BookUpdated`, `BookPriceChanged`). Потрібна, щоб форма оформлення видачі не робила синхронний виклик до Каталогу на кожне читання. Механізм подій — Лаб. 08; до того копія синхронізується `seed`/скриптом (`MERGE` у `seed.sql`). |
| 3 | `Books.CopiesAvailable` | `LibraryLendingDb` (Проєкт №1) | **Власник — Проєкт №1** (а не Каталог) | **Не дублювання, а власні дані контексту Видачі.** Залишок доступних для видачі примірників змінюють саме операції видачі/повернення, тому `seed.sql` його не перетирає (`MERGE ... WHEN MATCHED` оновлює все, крім цього поля). `Catalog.Books.AvailableCopies` — окреме поле з іншим змістом: скільки примірників узагалі є на балансі. |
| 4 | `reviews.bookTitle`, `discussions.bookTitle`, `readingLists.items[].bookTitle` | `LibraryReviewsDb` (Проєкт №3) | `Books` у `LibraryCatalogDb` (Проєкт №2) | **Копія для читання — оновлюється подіями з Каталогу.** Денормалізація дає змогу показати список відгуків без жодного звернення до Каталогу. |
| 5 | `reviews.author.displayName`, `readingLists.owner.displayName`, `readerProfiles.displayName` | `LibraryReviewsDb` (Проєкт №3) | `Readers` у `LibraryLendingDb` (Проєкт №1) | **Знімок імені на момент публікації — НЕ оновлюється.** Відгук підписаний тим іменем, під яким його опублікували. Відгук може бути й анонімним — тоді `readerId` відсутній узагалі. |
| 6 | `LoanStatusHistory.ToStatus` | `LibraryLendingDb` | **Власні дані контексту** | Не дублювання: журнал подій агрегату Loan. |

### Чому дублювання допустиме і що ми втрачаємо

Дублювання **роз'єднує сервіси**: сервіс Видачі читає назву книги зі своєї бази й не
падає, коли Каталог недоступний. Натомість ми втрачаємо строгу узгодженість —
між зміною в Каталозі й оновленням копії є вікно, протягом якого дані розходяться
(**eventual consistency**).

**Неприпустимий випадок (dual write)**, якого в цьому проєкті немає: дві копії поля,
які **незалежно редагуються** в різних сервісах без визначеного власника. Тому для
кожного рядка таблиці вище вказано рівно одного власника даних.

## 6. Обґрунтування вибору первинних ключів

| Таблиця | PK | Обґрунтування |
|---|---|---|
| `Readers`, `Loans`, `LoanStatusHistory`, `FinePayments` | `BIGINT IDENTITY(1,1)` | Вставка йде **лише з одного джерела** — сервісу Видачі. Послідовні значення дають компактні, не фрагментовані індекси. GUID тут був би зайвими 8 байтами в кожному індексі. |
| `LibraryLendingDb.Books` | `BIGINT` **без** `IDENTITY` | Id **приходить із Каталогу** — це той самий ідентифікатор, що й `LibraryCatalogDb.Books.Id`. Генерувати його тут заборонено. |
| `LoanDetails` | `BIGINT` = FK на `Loans` | Зв'язок 1:1: PK залежної таблиці є водночас зовнішнім ключем, тому фізично неможливо мати два рядки деталей на одну видачу. |
| `LoanItems`, `BookGenres` | складений `(LoanId, BookId)` / `(BookId, GenreId)` | M:N: складений ключ сам гарантує, що пара не повториться. |
| `LibraryCatalogDb.Books` | `BIGINT IDENTITY(1,1)` | Власник ідентифікатора книги; вставка лише з сервісу Каталогу. |
| `Authors`, `Genres` | `INT IDENTITY(1,1)` | Невеликі довідники, `BIGINT` не потрібен. |
| `reviews`, `discussions`, … | `ObjectId` | Стандарт MongoDB: генерується на клієнті, містить часову компоненту, не потребує звернення до сервера. |

## 7. Аудит, м'яке видалення та конкурентність (Крок 6)

- **Аудитні колонки** `CreatedAt`, `CreatedBy`, `UpdatedAt`, `UpdatedBy` — у
  `Readers`, `Loans`, `Authors`, `Books` (обох баз).
- **М'яке видалення** `IsDeleted BIT` — у `Readers`, `Loans`, `Authors`, `Books`,
  `Genres`. Фільтровані індекси (`WHERE IsDeleted = 0`) обслуговують лише «живі»
  записи й тому менші за розміром.
- **Оптимістична конкурентність** `ROWVERSION` — у `Readers`, `Loans`, `Books`
  (обох баз). Обґрунтування вибору: конкурентні записи одного рядка тут **рідкі**
  (двоє бібліотекарів нечасто редагують ту саму видачу), тому `optimistic` дешевша
  за постійні блокування. Конфлікт виявляється під час запису і повертається
  клієнту як `409 Conflict`.
- **Песимістичне блокування** застосовано точково — у збережуваних процедурах
  (`WITH (UPDLOCK)` при читанні статусу перед його зміною). Тут конфлікт потрібно
  **запобігти**, а не виявити: два паралельні підтвердження видачі не повинні
  обидва зменшити залишок примірників.
- **Компроміс рівня ізоляції:** усі бізнес-транзакції працюють на
  `READ COMMITTED` (значення за замовчуванням SQL Server). Вищий рівень
  (`REPEATABLE READ`, `SERIALIZABLE`) прибрав би фантомні читання, але різко
  збільшив би кількість блокувань і ризик deadlock на `dbo.Books` — найгарячішій
  таблиці. Там, де потрібна стабільність рядка в межах транзакції, це досягається
  точковою підказкою `UPDLOCK`, а не підняттям рівня для всієї транзакції.
- **Ідемпотентність** ключових операцій: `FinePayments.IdempotencyKey UNIQUE` —
  повторна відправка запиту на оплату пені не створить другий платіж.

## 8. Статуси видачі та допустимі переходи

За зразком `OrderStatus` з референсного застосунку Microsoft eShop:

```
Submitted ──► AwaitingValidation ──► CopiesConfirmed ──► Issued ──► Returned
    │                 │                     │
    └─────────────────┴─────────────────────┴──────► Cancelled
                                                     (лише ДО видачі на руки)
```

| Перехід | Процедура | Відмова, якщо |
|---|---|---|
| → `CopiesConfirmed` | `usp_ConfirmLoanCopies` | статус не `Submitted`/`AwaitingValidation` → **50002**; немає позицій → 50004; не вистачає примірників → **50003** |
| → `Issued` | `usp_IssueLoan` | статус не `CopiesConfirmed` → **50002**; не вистачає примірників → **50003** |
| → `Returned` | `usp_ReturnLoan` | статус не `Issued` → **50002** |
| → `Cancelled` | `usp_CancelLoan` | книги вже видані на руки → **50002** |

Коди помилок процедур перетворюються на HTTP-статуси в Лаб. 02:
**50001 → 404**, **50002 / 50003 / 50004 → 409**.
